Subagents Pattern (Hierarchical Supervisor)

Core Concept: A main agent coordinates subagents as tools. All routing passes through the main agent.

Topology: Star / Hub & Spoke
LangChain Architecture Diagram

How It Works

The user talks exclusively with the Main Agent. Subagents (e.g. Research Agent, Coder Agent, Writer Agent) are exposed to the main agent as callable tools. When a complex query arrives, the main agent invokes subagents to perform focused tasks, collects their responses, and synthesizes the final reply for the user.

Key Advantages
  • Clean context window isolation for subagents.
  • Main agent maintains strict control over final user response.
  • Subagents can be developed and evaluated independently.
Trade-offs & Limits
  • Main agent is a bottleneck for every turn.
  • High token cost: outputs pass through main agent context.
  • Subagents cannot talk directly to the user.
// LangChain Implementation Primitive
research_tool = create_subagent_tool(subagent=researcher)
main_agent = create_agent(model=llm, tools=[research_tool, code_tool])

Handoffs Pattern (Peer Swarm / Dynamic Delegation)

Core Concept: Agents transfer control to each other via tool calls. Each agent can hand off to others or respond directly to the user.

Topology: Decentralized Mesh / Swarm
LangChain Architecture Diagram

How It Works

There is no central coordinator. Specialized agents form a team. An active agent interacts directly with the user. When an issue requires a different domain expert (e.g. Underwriting escalating to Loan Structurer, or Tech Support handing off to Billing), the active agent calls a handoff tool that emits a Command(goto="target_agent", graph=Command.PARENT). Control and state transfer directly to the peer agent!

Key Advantages
  • No supervisor bottleneck or central point of failure.
  • Direct, conversational interaction between user and specialist.
  • Dynamic, non-linear workflows with cyclic loops and returns.
Trade-offs & Limits
  • Requires clear protocol so agents do not ping-pong forever.
  • Must track active_agent across multi-turn sessions.
// LangGraph Implementation Primitive
return Command(goto="loan_structurer", graph=Command.PARENT, update={"active_agent": "loan_structurer"})
Workspace Reference: Seen in Mortgage_Underwriting_Handoffs_Notebook_5.ipynb and Customer_Support_Swarm_Network_Notebook_6.ipynb.
3

Skill-Based Pattern (Progressive Context Disclosure)

Core Concept: A single agent loads specialized prompts and knowledge on-demand while staying in control.

Topology: Single Agent + Modular Knowledge
LangChain Architecture Diagram

How It Works

Rather than spawning multiple agents, a single master agent remains in charge from start to finish. Instead of cramming all database schemas, API specs, and domain guidelines into the system prompt upfront (which wastes tokens and causes prompt drift), the agent uses skills: modular packages containing domain instructions, documentation, and tools loaded dynamically only when needed.

Key Advantages
  • Maximum token efficiency (progressive disclosure).
  • Consistent single-agent persona and conversation memory.
  • Easily extensible: add new skills without altering graph edges.
Trade-offs & Limits
  • Requires the model to recognize which skill to fetch.
  • No parallel execution across distinct worker threads.
// Skills Implementation Primitive
@tool
def load_skill(skill_name: str) -> str:
    return read_file(f"skills/{skill_name}/SKILL.md")
Workspace Reference: Seen in SQL_Agent_HITL_PII_Notebook_2.ipynb and the Antigravity Customization Skills system.
4

Router Pattern (Classifier / Parallel Fan-Out & Synthesizer)

Core Concept: A routing step classifies input and directs it to specialized agents. Results are synthesized.

Topology: Split -> Parallel Execute -> Merge / Reduce
LangChain Architecture Diagram

How It Works

An upfront Router / Classifier analyzes the user query to categorize it or decompose it into distinct verticals (e.g. querying GitHub, Notion, and Slack simultaneously, or benchmarking multiple frameworks). The tasks are dispatched in parallel to specialized agents. Once completed, a downstream Synthesizer / Reducer node aggregates their results into a cohesive deliverable.

Key Advantages
  • High concurrency & speedup via parallel execution.
  • Clear separation of distinct data sources / domains.
  • Deterministic aggregation at the synthesizer step.
Trade-offs & Limits
  • Requires a clear classification boundary upfront.
  • Less suitable for back-and-forth multi-turn chat.
// LangGraph / LangChain Implementation Primitive
builder.add_conditional_edges("router", fanout, ["agent_a", "agent_b", "agent_c"])
builder.add_edge(["agent_a", "agent_b", "agent_c"], "synthesize")

Which Multi-Agent Pattern Should You Choose?

Answer the interactive questionnaire below to find the best architecture for your production application.

Choose Subagents if: Hierarchical

• You need a single primary conversational agent that delegates background subtasks.
• Subtasks require completely isolated contexts (e.g., deep web browsing, code execution) so the main conversation remains clean.
• The user should only perceive talking to one centralized assistant.

Choose Handoffs if: Swarm

• You have clear, distinct stages (e.g., Intake → Underwriting → Structuring → Compliance).
• Each specialist agent needs to speak directly to the customer when it is their turn.
• Tasks involve cyclical escalation, loops, or returns to previous agents.

Choose Skill-Based if: Modular

• You want to keep the architecture simple with only one agent, avoiding multi-agent graph overhead.
• You have dozens of specialized documentation sets, guidelines, or database schemas.
• You want to save context window tokens by loading skills only when explicitly needed.

Choose Router if: Parallel Fan-Out

• Queries can be classified upfront into distinct verticals (e.g., Finance, Tech, HR).
• Tasks can be executed in parallel across multiple data sources or competitors simultaneously.
• All findings need to be merged together at the end into a single comparison report.
